# Flora Room Type, Arrival & Departure Intelligence — Technical Reference

This document is the complete, as-built specification of the dashboard: every
calculation, mapping, normalization rule, filter behaviour, upload/persistence
process, and visual specification currently implemented in
`room-type-db/`. It is written so you can paste it into a Claude.ai Project's
knowledge (or a fresh chat) and continue development there without losing any
existing logic.

Paired reference: `.claude/skills/flora-room-dashboard/PROJECT_CONTEXT.md` and
`PROJECT_INSTRUCTIONS.md` in this repository are the **original approved
spec**. This document describes the **actual implementation**, including
decisions made to resolve ambiguity and changes approved during the July 2026
enhancement round. Where the two differ, this document wins — it reflects
what the code in `room-type-db/` actually does today.

## 3. Data extraction & normalization rules (`normalization.js`)

### 3.1 Worksheet & header detection (`import.js` → `detectHeaders`)

- Every worksheet in the workbook is scanned; for each, the first 15 rows are
  checked and the row with the most alias-recognized headers becomes the
  header row.
- The worksheet with the **highest header-recognition score** across the
  whole workbook is auto-selected in the wizard (confirmed working: correctly
  ignores scrap/staging sheets and picks the real data sheet even when it
  isn't the first tab).
- The user can override the sheet and every column mapping manually in the
  wizard before committing.

### 3.2 Date normalization (`normalizeDate`)

Handles three input shapes and returns `'YYYY-MM-DD'` or `''`:

1. **JS `Date` object** — shifted forward 12 hours, then read with **UTC**
   getters. This "noon-shift" trick exists because of a real bug found in
   production: SheetJS's `cellDates: true` option can land a date-only cell a
   few seconds *before* local midnight depending on the machine's timezone
   (confirmed reproducing on Asia/Dubai: `2026-06-01` came back as
   `2026-05-31T19:59:48Z`). Shifting to noon before reading the UTC calendar
   date makes the result correct for any timezone offset within ±12 hours,
   verified across Asia/Dubai, UTC, America/New_York, Pacific/Kiritimati
   (UTC+14), and Pacific/Midway (UTC−11).
2. **Numeric Excel serial** — converted via `(serial − 25569) × 86400000`ms
   (25569 = days between the Excel epoch 1900-01-01 and the Unix epoch,
   using the standard 1900 leap-year-bug-compatible system), read with UTC
   getters. **This is the path actually used in production**: `import.js`
   deliberately calls `XLSX.read(..., { cellDates: false, raw: true })` so
   dates arrive as raw numbers, sidestepping the Date-object bug entirely.
3. **String** — tries `YYYY-MM-DD` first, then `DD/MM/YYYY` (Dubai locale
   assumption — **note**: this is ambiguous for day/month both ≤12; see
   §15), then falls back to `new Date(string)`.

### 3.3 Time normalization (`normalizeTimeMinutes`)

Returns minutes-since-midnight (0–1439) or `null`. Accepts:
- `Date` objects (local `getHours()/getMinutes()` — times don't carry the
  date-shift bug since only the hour/minute matter, not the calendar date)
- Excel time fractions (0–1, or the fractional part of a date-time serial)
- Strings: `HH:mm`, `HH:mm:ss`, `h:mm AM/PM` (regex:
  `^(\d{1,2}):(\d{2})(?::(\d{2}))?\s*(AM|PM)?$`)
- Anything else (blank, unparseable) → `null`, which maps to the
  `Unknown / Invalid Time` group and can **never** win a peak-hour calculation.

### 3.4 Number normalization (`normalizeNumber`)

- `null`/`undefined`/`''` → `null` (blank stays blank).
- Numeric type → returned as-is (or `null` if `NaN`/`Infinity`).
- String → commas stripped, then `Number()`; non-numeric strings → `null`.
- **Blank ≠ zero everywhere downstream** — every SUM function skips `null`
  rather than treating it as 0, and the Data Quality engine flags "Missing
  Arrival Rooms" / "Missing Departure Rooms" / "Missing or unavailable Room
  Nights" separately from legitimate zero values.

### 3.5 Text/code normalization

- `normalizeText` — trims and collapses internal whitespace.
- `normalizeCode` — same, plus uppercases. Applied to `Property`,
  `Market Code`, `Booked Room Type` on ingest, and to `Market Group` /
  `Account Manager` at grouping time (§5).
- Room Number, Confirmation Number, Phone Number, Rate Code use
  `normalizeText` only — **never uppercased, never number-coerced, leading
  zeros preserved** (verified: `'0447'` stays `'0447'`, not `447`).

## 4. Record key & duplicate/update classification

### 4.1 Primary key (`recordKey` in `normalization.js`)

```text
Property | Business Date | Confirmation Number | Room Number
| Booked Room Type | Arrival Date | Departure Date
```

### 4.2 Fallback key (used only when Confirmation Number is blank)

```text
'FB' | Property | Business Date | Guest Name | normalized Phone Number
| Room Number | Arrival Date | Departure Date
```
(prefixed `'FB'` so a fallback-key record can never collide with a
primary-key record). Phone is normalized to digits + leading `+` only for key
matching (`normalizePhoneForKey`); blank components become the token `~`.

### 4.3 Classification logic (`import.js` → `classify` / `classifyOne`)

For every incoming row, after `deriveGroups()`:

1. **Invalid** — if `Business Date` or `Property` failed to normalize
   (empty), the row is rejected and listed with reason/suggestion; not
   written to the database.
2. Build `key = recordKey(rec)` and `sig = contentSignature(rec)` (a
   concatenation of every standard field's string value).
3. **Intra-file duplicate check** (`seenInFile` map) — if this exact key
   already appeared earlier in the *same file*: identical signature →
   duplicate (skipped); changed signature → the later row replaces the
   earlier one in the new/update lists (last row in the file wins).
4. **Against the stored database** (`existingByKey` map, built from every
   currently stored record):
   - Key not found → **new record**, appended.
   - Key found, signature identical → **exact duplicate**, skipped, counted.
   - Key found, signature different → **update**; the *previous* full record
     is retained (for rollback) and the new version is written.
5. Side counters accumulated during classification: `unmappedRoomTypes`,
   `unmappedMarketGroups`, `unmappedAccountManagers` (Map of value → count),
   `invalidCombos` (Map of `"Property + RTG"` → count), min/max Business
   Date, distinct properties seen.

### 4.4 Large-file performance (`classifyAsync`)

`classifyAsync(candidates, existingByKey, onProgress)` processes rows in
chunks of 2,500 with a `setTimeout(step, 0)` yield between chunks, so the
main thread is never blocked long enough to freeze the tab, and the wizard
shows a live progress bar/label ("Classifying 25,000 of 42,702 rows…"). The
synchronous `classify()` still exists (used by the Node test harness) but the
UI always calls the async chunked version.

**Known limitation**: the initial `XLSX.read()` / `sheet_to_json()` parse of
the workbook itself is still synchronous (SheetJS has no chunked API) — for
very large workbooks (materially larger than the ~43k-row file this was
built against) that single parse step could still cause a noticeable pause
before the progress bar appears. If you need to handle much larger files,
this is the next place to optimize (e.g., a Web Worker running SheetJS off
the main thread).

```js
  label: '{hh}:00–{hh}:59', short: '{hh}:00', hour: h, from: h*60, to: h*60+59
});
```
Plus `Unknown / Invalid Time` for unparseable/missing times. **This replaced
the original 7-band grouping** (12am–5:59am, 6–8:59am, etc.) per the July
2026 change request — applied identically to Arrival Time and Departure Time
everywhere (distributions, heatmaps, peak calculations, pattern tables).

### 5.5 Occupancy Combination (dynamic, `deriveGroups`)

Generated from `Adults` + `Children` per row — **never a hardcoded list**:
- Both null, negative, non-integer, or both exactly 0 → `'Invalid'` (excluded
  from all combination visuals and metrics).
- Otherwise: `"{n} Adult(s)"` optionally + `" + {n} Child(ren)"`, e.g.
  `1 Adult`, `2 Adults`, `2 Adults + 1 Child`, `3 Adults + 5 Children`.

## 6. Physical inventory & occupancy validity

```js
PHYSICAL_INVENTORY = {
  FCHDXB: { BASE: 144, '2BHK CREEK': 12, '2BHK CHILD': 12, '2BHK MAID': 12 },  // 180 total
  FAHDXB: { BASE: 149, SUI: 12, CON: 24 },                                     // 185 total
  FIHDXB: { BASE: 155, SUI: 12, CON: 60 }                                     // 227 total
}
```

A record's `_validCombo` flag is `true` only if
`PHYSICAL_INVENTORY[Property]` exists **and** contains that record's Room
Type Group. Invalid combinations (e.g. SUI at FCHDXB, which isn't
configured there):
- Return `null`/`N/A` from `calculateAvailableRoomNights`.
- Are excluded from every occupancy numerator/denominator.
- Are counted and surfaced in Data Quality → "Invalid Property–Room Type
  combinations".

Inventory changes require editing `PHYSICAL_INVENTORY` in `constants.js` — a
deliberate design choice to keep occupancy denominators under change control
(no in-app inventory editor).

## 7. Calculation formulas (`calculations.js`)

All SUMs skip `null` (blank) — never coerced to 0, never row-counted.

| Metric | Formula |
|---|---|
| Arrival Rooms | `SUM(Arrival Rooms)` — Arrival Date basis |
| Departure Rooms | `SUM(Departure Rooms)` — Departure Date basis |
| Room Nights Sold | `SUM(Room Nights)` — Business Date basis |
| Arrival/Departure/Room-Night Share % | `part ÷ total_in_same_filtered_scope × 100`; `null` if total ≤ 0 |
| Available Room-Nights | `Physical Rooms × included calendar dates` (per valid Property+RTG combo) |
| Daily/Multi-day Occupancy % | `Room Nights Sold ÷ Available Room-Nights × 100` |
| Multi-property/multi-RTG Occupancy | **Sum sold, sum available, across every valid combo, then divide once** — never average per-combo percentages |
| Weighted Avg Arrival/Departure Time | `SUM(minutes × rooms) ÷ SUM(rooms with valid time)` |
| Peak Arrival/Departure Hour | the valid (non-Unknown) time group with the highest `SUM(rooms)`; **ties return every tied group** |
| Occupancy Combination metric | always `SUM(Arrival Rooms)` for that Adults+Children combo |
| Last-Year period | exact calendar-year shift (`shiftYear`, leap-day-safe: 2024-02-29 → 2023-02-28) |
| Variance (absolute) | `TY − LY`; `pct = LY=0 ? null : (TY−LY)/LY×100` — **never Infinity/NaN, shown as "N/A"** |
| Percentage-point variance | `TY% − LY%`, displayed as `+4.2 pp` |

### 7.1 Date spine & current-month capping (`dateSpine`, `includedDates`)

- `dateSpine(from, to)` — every calendar date in range inclusive, as
  `YYYY-MM-DD` strings, **including dates with zero records** (built by
  literal date iteration, not by "distinct dates present in data").
- `includedDates(from, to, latestBusinessDate)` — same, but clamped so `to`
  never exceeds `latestBusinessDate`. This is what makes "current month
  occupancy stops at the latest loaded Business Date" work: if today's data
  only goes to the 15th, the denominator uses 1–15, not 1–30/31.
- For a **completed historical period** (not the current month), the LY
  side of a comparison uses the plain `dateSpine` (no capping) since that
  period is, by definition, fully in the past.

### 7.2 Occupancy: exact algorithm (`calculateOccupancy`)

```js
function calculateOccupancy(records, combos, nDates) {
  // combos = [{property, rtg}] — the valid Property+RTG combinations in scope
  // 1. sum Room Nights per Property|RTG key, but ONLY for records where
  //    _validCombo is true (invalid combos silently contribute 0 here —
  //    they're surfaced separately in Data Quality, not double-counted)
  // 2. for each combo: available += PHYSICAL_INVENTORY[property][rtg] * nDates
  //                     sold += soldByCombo[property+'|'+rtg]
  // 3. return { pct: available>0 ? sold/available*100 : null, sold, available }
}
```
This is called with `Filters.state.properties` / `roomTypeGroups` narrowed
to `Calc.validCombos(...)` — so selecting multiple properties correctly sums
before dividing rather than averaging per-property percentages.

**Occupancy is never capped at 100%** — values above 100% are returned as-is
and flagged in Data Quality (category "Room Type Occupancy above 100%") for
the user to investigate, rather than silently clamped.

## 8. Global filters (`filters.js`)

### 8.1 Filter state shape

```js
Filters.state = {
  properties: [], roomTypeGroups: [], seggrps: [], months: [],       // primary
  marketCodes: [], accountManagerGroups: [], reservationStatuses: [],
  nationalities: [], occupancyCombos: [], weeks: [],                  // advanced
  dateFrom: '', dateTo: '',
  includeUnmapped: false,
  comparisonMode: 'both'   // 'both' | 'ty' | 'ly'
}
```
Persisted to `localStorage` (`flora_rtdb_filters_v1`) so selections survive a
page reload — **this is the only thing localStorage is used for**; all
tracker data lives in IndexedDB.

### 8.2 Date basis per section (`Filters.apply(records, dateBasis)`)

`dateBasis` is `'bd'` (Business Date), `'ad'` (Arrival Date), or `'dd'`
(Departure Date). The Month/Week/Date-range filters are applied against
whichever field matches the section being rendered — e.g. the Arrivals tab
filters by Arrival Date even though the global "Month" slicer conceptually
feels universal. This is deliberate per the original spec (§4: "Use the
correct date basis for each section").

### 8.3 Single-select-by-default / Ctrl-Cmd-multi (current behaviour, `ui.js`)

This was changed in the July 2026 round. Each option row in a multi-select
dropdown (`UI.multiSelect`) is a plain clickable `div`, not a checkbox:

- **Plain click** → replaces the entire selection with just that one value
  (selecting August automatically deselects July). Clicking the *only*
  currently-selected value again clears back to "All".
- **Ctrl+click or Cmd+click** → adds/removes that value from the existing
  selection (intentional multi-select).
- "Select All" / "Clear" buttons still set the whole list at once.
- A hint (`Click = single select · Ctrl/Cmd+click = multi`) is shown inside
  every dropdown panel.

This behaviour is generic in `UI.multiSelect` — it applies uniformly to
every filter group (Property, Room Type Group, SEGGRP, Month, Market Code,
Account Manager, Reservation Status, Nationality, Occupancy Combination,
Week) with no per-filter special-casing.

### 8.4 Defaults & reset

`Filters.applyDefaults(records)` — on first load (or Reset Filters), selects
**one property** (the alphabetically first one present) and the **latest
available Business-Date month** — never "all properties combined" unless the
user explicitly multi-selects.

### 8.5 UNMAPPED visibility

`includeUnmapped` (off by default) — when off, `Filters.apply` drops any
record whose Room Type Group or SEGGRP is `UNMAPPED`, from every consumer
(KPIs, charts, tables, exports). Toggling it on reveals them everywhere at
once, consistent with the "Include Unmapped" switch spec.

1. Duplicate records (stored records sharing a key — should be ~0 in normal

2. Unmapped Room Type Codes
3. Unmapped Market Groups
4. Unmapped Account Managers
5. Invalid Property–Room Type combinations
6. Missing Business Dates
7. Invalid Arrival Dates
8. Invalid Departure Dates
9. Invalid Arrival Times
10. Invalid Departure Times
11. Missing Arrival Rooms
12. Missing Departure Rooms
13. Missing Room Numbers
14. Missing Confirmation Numbers
15. Negative numeric values (checked across Room Nights, Arrival/Departure
    Rooms, Adults, Children, Revenue)
16. Room Type Occupancy above 100% (computed by the dashboard per
    Property+RTG combination in the current filter scope, passed in as
    `occupancyFlags` — not a raw per-row check)
17. Zero adults and zero children (on rows where Arrival Rooms > 0 — i.e. an
    arrival with no recorded guests)
18. Missing or unavailable Room Nights

## 10. Upload & persistence workflow

### 10.1 IndexedDB schema (`database.js`)

- DB name `flora_room_type_db`, version 1.
- `records` store, keyPath `key` (the record key from §4) — `put()`
  overwrites in place, giving natural upsert semantics.
- `batches` store, keyPath `batchId` — one row per completed upload,
  containing `addedKeys` (array, for rollback deletion) and `updatedPrev`
  (array of full previous-version records, for rollback restoration).
- `meta` store — reserved, currently unused beyond schema versioning.

### 10.2 Commit (`commitBatch`)

Single IndexedDB transaction across `records` + `batches`: every new/updated
record is `put()`, the batch metadata row is `put()`, and the transaction
either commits atomically or the whole import fails with nothing partially
written (`t.onerror`/`t.onabort` reject the promise).

### 10.3 Rollback (`rollbackBatch`)

Single transaction: deletes every key in `batch.addedKeys`, restores every
record in `batch.updatedPrev` to its pre-import state, and flags the batch
`rolledBack: true` with a timestamp. Verified in testing: append removed,
updated record's previous value restored exactly.

### 10.4 Wizard flow (`app.js`)

1. **Step 1 — Worksheet**: shows every sheet with row count + recognized-
   header score; best-scoring sheet pre-selected.
2. **Step 2 — Field Mapping**: every detected column with its auto-mapped
   standard field (or "(ignore)"); user can override any column.
   `Business Date` and `Property` are the only hard requirements — Next is
   blocked with a named error if either is unmapped.
3. **Step 3 — Preview**: runs `Importer.buildRecords` then
   `Importer.classifyAsync` with a live progress bar, then shows: total
   rows, new/updated/duplicate/invalid counts, any columns present in the
   file but not mapped (informational), unmapped room types/market
   groups/account managers with counts, invalid Property–RTG combinations,
   and up to 5 invalid-row examples with reasons. Confirm is disabled when
   there is genuinely nothing new/updated to import, with an explanatory
   note rather than a silent disabled button.
4. **Commit**: writes via `Importer.commit` → `DB.commitBatch`, then
   `reloadFromDb()` re-reads everything from IndexedDB and re-derives groups
   in memory, and every view re-renders (`buildFilterBar(); refresh();`).

### 10.5 Backup / restore / reset (`exports.js`, header Export menu)

- **JSON Backup** — full dump of `records` + `batches` with metadata
  (`exportedAt`, `recordCount`, `schemaVersion`).
- **Restore JSON Backup** — parses and validates the file has a `records`
  array, confirms with the user (record-count comparison shown), then
  atomically replaces both stores.
- **Reset Database** — requires literally typing `RESET` in a confirm
  dialog; clears all three IndexedDB stores.
- **Full Database CSV** / **Filtered Detail CSV** / **Filtered Summary CSV**
  / **Data Quality CSV** / **Upload History CSV** — all pull through the same
  `Filters.apply()` path as the on-screen visuals, so exports always match
  what's currently displayed.

## 12. Known limitations / likely sources of remaining data-extraction issues

Use this section to prioritize what to fix next:

1. **DD/MM/YYYY string-date ambiguity** (§3.2, case 3) — when both day and
   month are ≤12 in a string date (not a serial, not a Date object), the
   parser assumes Dubai locale (DD/MM). If any source ever exports US-style
   MM/DD strings, this would misparse silently. The Excel workbook tested
   against uses Date objects/serials, not ambiguous strings, so this hasn't
   surfaced yet — but it's a latent risk worth a defensive check (e.g., warn
   if day > 12 would have been valid as a month).
2. **Synchronous initial parse** (§4.4) — `XLSX.read`/`sheet_to_json` is not
   chunked; only classification is. A much larger workbook than the ~43k-row
   test file could still cause a momentary freeze before the progress bar
   appears. A Web Worker would fully solve this.
3. **Reservation count heuristic** (Guest Occupancy Combinations matrix,
   "Reservations" metric) — since there's no single canonical reservation ID
   field guaranteed across all rows, `Confirmation Number` is used, falling
   back to `Guest Name + Arrival Date` when blank. This is an approximation,
   not an exact count, and should be revisited if a true reservation ID
   field becomes available.
4. **Floor Analysis occupancy denominator** — no per-floor physical
   inventory exists in the approved configuration, so occupancy is computed
   from rooms *observed in the loaded data* per floor, not a configured
   floor capacity. This is noted in the UI tooltip but is a genuine
   approximation.
5. **Account Manager and Room Type mapping tables are hardcoded** in
   `constants.js` — any new code/name appearing in future exports lands in
   `UNMAPPED`/gets flagged in Data Quality rather than breaking anything,
   but nobody is notified proactively; check the Data Quality tab after each
   upload.
6. **`localStorage` filter persistence** — if a user has filters selected
   referencing values (e.g., a Room Type Group) that no longer exist in a
   freshly restored/reset database, `Filters.applyDefaults` silently drops
   invalid selections back to computed defaults on next load — this is
   correct behavior but worth knowing about if filter state ever "resets
   unexpectedly" after a restore.
